# 模擬模式說明

這份文件說明遊戲背後的運輸模式怎麼算、參數怎麼來的、以及**哪些是真實資料、哪些是推估**。

---

## 一句話版本

簡化的四階段運輸模式：先算出誰想從哪去哪（與路網無關，建 pack 時算好），
再算他們會不會搭大眾運輸、走哪條路徑，最後統計運量、涵蓋率、通勤時間與財務。

---

## 資料的可信度分級

| 資料 | 等級 | 說明 |
|---|---|---|
| 村里與行政區界 | **真實** | 內政部圖資，簡化至 10t 精度 |
| 各區人口 | **真實** | 內政部戶政司，民國 106 年，雙北 41 區全數對應，總計 6,669,946 人 |
| 台北捷運站點與站序 | **真實** | 由 OpenStreetMap 的 route relation 擷取，116 站 |
| 台北捷運線色 | **真實** | 官方線色 |
| 村里層級人口 | **推估** | 由區級往下分配，見下方「人口分配」 |
| 就業分布 | **推估** | 無開放資料，以就業中心模型合成，見下方「就業推估」 |
| 各運具造價 | **量級估計** | 台灣工程實務的數量級，非決算數字 |
| 真實捷運尖峰班距 | **量級估計** | 來源資料自標為估計值且偏長，已用各線公開的尖峰班距量級覆寫 |

> 結論：這個模擬**適合用來比較不同規劃方案的相對優劣**，
> 不適合當作工程可行性或財務評估的依據。

## 人口分配（區 → 村里）

台灣沒有開放的村里級人口資料，只能由區級往下推估。做法是：

```
權重_i = min(面積_i, 該區村里面積中位數 × 2)
人口_i = 該區總人口 × 權重_i / Σ權重
```

面積上限的用意是處理士林、北投、新店這類含大片山地的區。一個里再大，
超出上限的部分視為未開發土地，不再分到更多人口。

分配後會斷言「各村里人口加總 = 區級總人口」，確保沒有憑空生出或漏掉人。

實作：`scripts/build-city-pack.ts`

## 就業推估

就業分布直接決定通勤流向，是整個模擬最關鍵、也最沒有真實資料支撐的一環。

做法是在 `scripts/taipei-config.ts` 列出 16 個**具名的就業中心**
（台北車站、信義計畫區、內湖科技園區、板橋新板特區…），
每個中心有位置、就業數與衰減半徑，然後：

```
zone 分到的工作 = 人口 × 0.25                              （地方性就業）
               + Σ_中心 中心就業數 × exp(-距離/半徑) × 人口^0.25 / 正規化
```

兩個容易踩到的地方，都已經在校準時發現並修正：

1. **`人口^指數` 的指數不能太大。** 一開始用 `sqrt`（0.25 的兩倍），
   結果中正區、信義計畫區這種「居住人口低但工作機會多」的商業區被嚴重低估，
   台北車站的運量掉到第 17 名。改成 0.25 之後才合理。

2. **衰減半徑不能為了「加強」某個中心而放大。** 半徑放大會把工作攤散到走不到的地方，
   反而讓該站的運量下降。台北車站一度設成 1.6 km，800 公尺內只分到 24 萬個工作中的 3.1 萬個；
   壓回 1.0 km 之後才回到運量前三名。

## 四個階段

### 1 & 2. 行程產生與分布（建 pack 時算好）

雙約束重力模型 + Furness/IPF 疊代：

```
T_ij = a_i · b_j · P_i · A_j · exp(-β · c_ij)
```

- `P_i` 產生量 = 人口 × 每人每日行程數 × 尖峰小時占比
- `A_j` 吸引量 = 就業機會（等比例縮放到與總產生量相等）
- `c_ij` 小汽車旅行時間 = 直線距離 × 繞路係數 ÷ 車速
- `β = 0.02`（每分鐘）

**排除區內旅次**（i = j）：那多半是步行或機車可達的短程，不是路網的服務對象，
納入只會稀釋運具分擔率的解讀。

**這一步與玩家的路網完全無關**，所以整個烘焙進 city pack。
執行期改線時不用重算，這是能做到即時回饋的關鍵。

稀疏化：每個起點只保留權重最高的前 50 個目的地，被捨棄的流量按比例補回保留的目的地，
確保每個 zone 的總產生量不變（有單元測試驗證）。1465 個 zone → 73,250 組起訖對。

### 3. 運具選擇

二元 logit，比較大眾運輸與私人運具的廣義時間：

```
P(搭乘) = 1 / (1 + exp(logitConstant + logitTimeCoef × (T_大眾 − T_私人)))
```

`T_大眾` = 步行進站 + 候車（班距/2）+ 車內時間 + 轉乘罰值 + 步行出站

**道路壅塞回饋**：搭乘的人越多 → 路上車越少 → 開車越快 → 又有人改開車。
用 BPR 型函數迭代到穩定（通常 2–3 次）：

```
車速 = 自由流速度 / (1 + α × (車流/道路容量)^β)
```

這一段不是裝飾。**少了它，模擬會得出「蓋捷運讓平均通勤時間變長」的荒謬結論** ——
因為模型裡搭車的人本來就比開車慢（30 分 vs 24 分），卻沒有任何人因為道路變空而受益。
加上壅塞回饋後，真實捷運路網讓全體平均旅行時間從 26.6 分降到 23.9 分。

### 4. 路網指派

建圖（`src/sim/graph.ts`）：

- **車站節點**（街道層，步行進出與轉乘都經過這裡）
- **月台節點**（每一組「路線 × 車站」一個）
- 車站→月台 = 上車，成本為候車時間
- 月台→車站 = 下車，成本為轉乘罰值
- 月台→月台 = 行駛，成本為車內時間

轉乘罰值掛在「下車」而不是「上車」，這樣每多轉一次車就多付一次罰值。
直達的行程也會付到一次（最後一次下車），所以最終旅行時間要扣掉一個罰值 ——
那是對所有大眾運輸路徑都相同的常數，不影響最短路徑排序。

**效能關鍵：從車站而不是從 zone 出發跑 Dijkstra。**
車站數是幾百，zone 數是 1465，差一個數量級。
zone 透過 800 公尺步行連結接上鄰近車站（最多 6 個），
zone 到 zone 的時間 = `min over (進站 a, 出站 b)` 的 `步行 + T[a][b] + 步行`。

指派時依「進站車站」把起訖對分組，每個車站只需再跑一次 Dijkstra
就能追溯它所有起訖對的路徑，不必把所有起點的前驅陣列都存在記憶體裡。

全網模擬約 **50–70 ms**。

## 校準

`npm run calibrate` 把**真實的台北捷運路網**餵進模擬器，跟現實對照。
模擬器如果連現實中已經存在的路網都算不準，玩家自己畫的路網得到的數字就沒有意義。

目前的結果：

| 項目 | 模擬 | 現實 |
|---|---|---|
| 全日運量 | 2,082,485 | 約 210 萬人次 |
| 最繁忙路線 | 板南線（負載率 85%） | 板南線 |
| 台北車站運量排名 | 第 3 | 第 1 |
| 人口涵蓋率（800m） | 48.5% | — |
| 建設成本 | 9,449 億 | 約 7,000–9,000 億 |
| 年營運成本 | 199 億 | 約 180 億 |
| 年票箱收入 | 190 億 | 約 180 億 |
| 票箱回收率 | 95% | 約 100–110% |

站點運量排序（中山、忠孝復興、台北車站、台北101/世貿、台北小巨蛋、善導寺、忠孝新生、
南京復興、北門、西門…）與實際的台北捷運大站名單高度吻合。

### 已知偏差

**台北車站在模擬中排第 3 而非第 1。** 這是結構性的：模擬裡沒有台鐵、高鐵與國道客運，
台北車站作為城際轉運節點的那一大塊集散量完全缺席。因此校準只要求它進入前 5 名，
而不是硬把參數調到讓它排第一。

**最大斷面客流偏低。** 就業中心用指數衰減分布，比現實中的商業區更分散，
因此尖峰斷面的集中程度不如實際。相對比較仍然有效。

### 參數

都在 `src/model/defaults.ts` 的 `DEFAULT_SIM_PARAMS`：

| 參數 | 值 | 說明 |
|---|---|---|
| `gravityBeta` | 0.02 | 每分鐘的距離衰減。調大 → 旅次變短、大眾運輸更沒競爭力 |
| `logitConstant` | −0.80 | 越大越偏好開車。這是調整總運量最直接的旋鈕 |
| `logitTimeCoef` | 0.11 | 對時間差的敏感度 |
| `transferPenaltyMin` | 5 | 轉乘的等效時間罰值 |
| `maxWalkM` | 800 | 願意走去車站的最大距離 |
| `carFreeFlowSpeedKmh` | 32 | 無壅塞時的車速 |
| `roadCapacityPeakTrips` | 1,920,000 | 尖峰道路容量，設成接近尖峰總旅次代表現況已在容量邊緣 |

改完參數要重跑 `npm run build:pack && npm run calibrate`
（`gravityBeta` 會影響烘焙進 pack 的起訖矩陣，一定要重建）。
